# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project rules

Two rules are mandatory in this repository and are re-injected at session start by
`.claude/hooks/context7-graphify-reminder.sh` (wired to `UserPromptSubmit` in `.claude/settings.json`).

- **context7**: for any question about a library, framework, SDK, API, or CLI tool (syntax,
  configuration, version migration, setup, library-specific debugging), use the context7 MCP
  server first — `resolve-library-id`, then `query-docs`, one concept per call — and answer from
  those docs rather than memory. Not for refactoring, scripting from scratch, or business logic.
- **graphify**: for any question about this codebase's architecture, modules, or file
  relationships, use the `graphify` skill first (it reads or builds `graphify-out/`, which is
  gitignored), then fall back to file search.

`APP_E2E=1 electron-forge package` because Playwright attaches to the main process through
`--inspect`, which the production fuse disables.

## Architecture

Electron app with three processes and an oRPC (type-safe RPC) transport over a `MessagePort`.
The renderer has no Node access at all.

```
main.ts ──(ipcMain MessagePort upgrade)── preload.ts ──(window.postMessage)── ipc/manager.ts
   │                                                                            │
   ├── ipc/router.ts → namespaces (app, customers, dialog, preferences,
   │                    shell, theme, window)                             ipc.client
   │        handlers.ts (os procedures) + schemas.ts (zod in/out)
   └── db/ (better-sqlite3 + Drizzle) · preferences/ (electron-store)
```

**Main process** (`src/main.ts`): single-instance lock; `hardenSession()` denies every web
permission and download; preferences are initialised and the stored theme applied *before* the
window, the database is initialised *before* the window, and the oRPC listener is registered
*before* `createWindow()` (the renderer posts its MessagePort while evaluating its bundle). The
window stays hidden until `ready-to-show`; a saved maximized state is restored there, because
`maximize()` shows the window. `window.open`, navigation, redirects and subframe navigation away
from the app are blocked. `isDevelopment` is `!app.isPackaged` on purpose — Forge does not set
`NODE_ENV`.

**Preload** (`src/preload.ts`) only forwards the `MessagePort` from the renderer's
`window.postMessage` to `ipcRenderer.postMessage`. It runs under `sandbox: true` with
`nodeIntegration: false` and `contextIsolation: true`; keep it dependency-free.

**Renderer**: `src/renderer.ts` → `src/app.tsx` (syncs theme + language, mounts `RouterProvider`).
TanStack Router uses `createMemoryHistory`, so routing is in-memory and there is no URL the app
will navigate to — that is why production navigation is restricted to the bundled entry file.
`src/routeTree.gen.ts` is generated by the router plugin; never edit it. The application shell
lives in `src/layouts/` (`base-layout.tsx` owns the `SidebarProvider`, `app-sidebar.tsx` the
navigation, `site-header.tsx` the header); routes render inside it and stay navigation-free.

**Renderer → IPC access** always goes through `src/actions/*.ts`, which are thin typed wrappers
around `ipc.client.<namespace>.<procedure>()`. Components import actions, never `ipc` directly.

### Adding or changing an IPC procedure

1. `src/ipc/<namespace>/schemas.ts` — zod `.strict()` input and output schemas. The transport is
   JSON, so wire types must be JSON-safe: timestamps are epoch milliseconds, never `Date`.
2. `src/ipc/<namespace>/handlers.ts` — `os.input(...).output(...).handler(...)`. Mutations throw
   `ORPCError` (e.g. `NOT_FOUND`); lookups return `null`. Errors are masked toward the renderer and
   logged by the interceptor in `src/ipc/handler.ts`, which only logs 5xx as real errors.
3. `src/ipc/<namespace>/index.ts` — add the procedure to the exported namespace object (this is
   what feeds the `RouterClient` type).
4. `src/ipc/router.ts` — only when adding a new namespace.
5. `src/actions/<name>.ts` — wrapper for the renderer.

Window-scoped procedures use the `os.use(ipcContext.mainWindowContext)` middleware from
`src/ipc/context.ts`. Existing filename/property quirks: `src/ipc/window/hadlers.ts` (not
`handlers.ts`) and `app.currentPlatfom`; renaming them changes the public router shape.

### Database

`src/db/index.ts` owns a disposable SQLite **cache** in Electron's `userData` (`cache.db`) using
better-sqlite3 + Drizzle, with migrations applied on startup.

- `APP_CACHE_DB_PATH` overrides the file (must be absolute, or `:memory:` in tests);
  `APP_CACHE_SKIP_INTEGRITY_CHECK=1` skips the dev-only `quick_check`.
- The safety rules here are load-bearing, not incidental: an `application_id` sentinel
  (`0x43414348`, "CACH") proves ownership, a non-SQLite header / symlink / hard link / foreign
  database is refused without modifying the file, corruption resets in place or moves the file
  aside as `cache.db.corrupt-<timestamp>` — it is never deleted — and permissions are tightened to
  `0600` (`0700` on the parent only for the default `userData` location).
- The migrations folder is located by walking up from `app.getAppPath()` (plus `resourcesPath` and
  `app.asar.unpacked`) so the same code works in dev, in `app.asar` and packaged; Forge ships it
  via `extraResource`.
- `src/db/schema.ts`: `customers` is keyed by `folderPath`. `searchText` is a pre-folded
  (NFC + lowercase) concatenation maintained by `upsertCustomer`, so `instr()` searches work
  without per-row JS.
- CI fails on schema drift: after changing the schema, run `npm run db:generate` and commit
  `drizzle/` (snapshots included).

### Preferences

`src/preferences/` wraps electron-store in the main process for the user
preferences: theme, language, folder directories and window state (`preferences.json` in
`userData`). The package is ESM-only and is bundled into the CJS main bundle; keep it in
`dependencies` but never import it from the renderer.

- `src/preferences/schema.ts` holds the zod schemas used by the IPC layer and the JSON
  Schema electron-store validates against.
- `src/preferences/store.ts` initialises after `app.whenReady()` and degrades to defaults
  when the file cannot be read. It refuses symlinks, non-regular files and files over 64 KiB,
  writes `0600`, and honours `APP_PREFERENCES_DIR` (absolute) only in development/E2E builds.
- Theme is applied to `nativeTheme.themeSource` before the window is created and persisted
  by the theme handlers. Language and the folder directories are exposed through the
  `preferences` oRPC namespace (`getFolders`/`setFolder`). Window bounds are restored in
  `createWindow` and saved on a debounce from `resize`/`move`, plus `maximize`, `unmaximize`
  and `close`.

### Dialogs

`src/ipc/dialog/` wraps `dialog.showOpenDialog` in the main process, parented to the main window.
`dialog.openFile` accepts `title`, `defaultPath`, `buttonLabel`, `filters`, `multiple` and
`showHiddenFiles`; `dialog.openDirectory` accepts the same without `filters`. `defaultPath` must
be absolute and non-UNC; filter extensions are normalised (`.png`/`*.png` → `png`), and the raw
Electron `properties` array is not exposed. Both procedures return `{ canceled, filePaths }`.
Native dialogs are not e2e-tested.

### Build and packaging

Electron Forge with the Vite plugin and three configs: `vite.main.config.mts`,
`vite.preload.config.mts`, `vite.renderer.config.mts` (Tailwind v4, TanStack Router plugin,
React Compiler via Babel). `@` aliases to `src` in `tsconfig.json` and in every Vite/Vitest config —
keep them in sync. `better-sqlite3` is externalised from the main bundle and re-added in Forge's
`packageAfterCopy` hook (per-platform prebuilds; `linuxmusl` too), because the Vite plugin only
copies `.vite` output. Fuses disable `RunAsNode`, `NODE_OPTIONS` and CLI inspect — except
`EnableNodeCliInspectArguments`, which stays on only for `APP_E2E=1` builds. The renderer's CSP
is in `index.html`.

### Tests and CI

- Vitest: jsdom, `src/tests/unit`, `setup.ts` registers jest-dom. Coverage thresholds are enforced
  and differ by area (global 55% statements/branches/lines and 38% functions; `src/db/**` 80–90%;
  `src/ipc/**` 85%+; `src/ipc/customers/**` 85–90%) — new untested code can
  fail CI even when tests pass. Entry points, `components/ui/**` and `routeTree.gen.ts` are
  excluded.
- Playwright: `src/tests/e2e`, `workers: 1` (the app holds a single-instance lock), launches the
  packaged executable via `electron-playwright-helpers`. `helpers.ts` allows only an env allowlist
  into the app and redirects `HOME`/`APPDATA`/`XDG_CONFIG_HOME` to a per-test temp dir; it also
  points `APP_PREFERENCES_DIR` and `APP_USER_DATA_DIR` at that temp dir (macOS resolves `userData`
  through the OS account, not `$HOME`, so this is what isolates the single-instance lock) and
  forwards `XAUTHORITY` so Electron can authenticate with `xvfb-run` on Linux CI.
- Workflows: `check.yaml` (`npm audit --omit=dev`, typecheck, `ultracite check`, `drizzle-kit
  check`, schema-drift check), `testing.yaml` (unit coverage; e2e under xvfb), `publish.yaml`
  (manual dispatch on a Windows runner, refuses `APP_E2E` builds, creates a **draft** GitHub
  release). Auto-update reads releases from `claudiodema93/prd-manager`.

### Theme and localization

Theme is three-state (`light`/`dark`/`system`) owned by `nativeTheme` in the main process; the
renderer mirrors the result onto `document.documentElement.classList` and, in `system` mode,
follows `matchMedia` so OS changes apply live. Each language lives in
`src/localization/resources/<code>.ts` (currently `it.ts`, whose keys also define the typed
`TranslationKey`), registered in `src/localization/i18n.ts`; the language list is
`src/localization/langs.ts`. To add a language, copy `resources/it.ts` to a new file with the same
keys, register it in `i18n.ts`, and add its entry to `langs.ts`. Both theme and language
preferences persist in electron-store (`src/preferences/`), not `localStorage`.

## Code style

Ultracite (Biome presets) enforces formatting and linting — run `npm run fix` before committing.
Beyond what the linter fixes automatically (see `.github/copilot-instructions.md`): prefer explicit
types where they add clarity and `unknown` over `any`; arrow functions for callbacks and `for...of`
over `.forEach`; early returns over nesting; `Error` objects with descriptive messages; no
`console.log`/`debugger`/`alert` in production paths; semantic HTML and ARIA for interactive UI;
`rel="noopener"` with `target="_blank"`; no barrel files. Biome ignores `src/components/ui/**`,
`src/routeTree.gen.ts`, `drizzle/` and `graphify-out/`.

Validate anything crossing the IPC boundary in its zod schema: paths are resolved and NUL-checked,
`metadataJson` is bounded (depth 8, 1000 nodes, 64 KiB), and `shell.openExternalLink` accepts only
`http:`/`https:`.
